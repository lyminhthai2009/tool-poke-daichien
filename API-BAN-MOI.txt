### 3.2. Cấu Trúc Header Nhị Phân 16-Bytes (Packet Framing) - [ĐÃ GIẢI MÃ HOÀN TOÀN]

> [!CAUTION]
> **Phát hiện dịch ngược đặc biệt quan trọng (Reverse Engineered từ `libHOGame.so`):**  
> Bốn byte đầu tiên (`Byte 0 – 3`) **KHÔNG PHẢI LÀ MAGIC ID CỐ ĐỊNH**. Nếu client gửi các giá trị tĩnh như `08 11 84 92` hoặc `49 c5 24 fc` với độ dài payload khác nhau, server sẽ **ngắt kết nối TCP ngay lập tức** (Disconnect at byte 15) do kiểm tra mã checksum thất bại!  
> Bản chất của 16-byte Header là hệ thống **kiểm tra toàn vẹn lồng 2 tầng CRC32 (Nested CRC32 Checksum)** của engine `SJ::Net::Message::encode`.

#### Bảng Cấu Trúc Chi Tiết 16 Byte Header:

| Vị trí Byte | Kiểu dữ liệu / Endian | Tên trường | Ý nghĩa & Quy luật tính toán |
| :---: | :---: | :--- | :--- |
| **Byte 0 – 1** | `uint16` (Big-Endian) | **Header Checksum (`crc2`)** | $\text{CRC32}(\text{Header}[2:16]) \ \& \ \text{0xFFFF}$. Tính CRC trên 14 byte sau của chính Header. |
| **Byte 2 – 3** | `uint16` (Big-Endian) | **Body Checksum (`crc1`)** | $\text{CRC32}(\text{Packet}[4:]) \ \& \ \text{0xFFFF}$. Tính CRC từ byte 4 đến hết toàn bộ payload. |
| **Byte 4 – 6** | `uint24` (3 Bytes Big-Endian) | **Packet Length** | Tổng độ dài toàn bộ gói tin = $16 + \text{len(payload)}$. |
| **Byte 7** | `uint8` (1 Byte) | **Packet Flag** | `0x0A`: Gói Handshake khởi tạo kết nối.<br>`0x00`: Gói dữ liệu ứng dụng thông thường.<br>`0x0B`: Gói Handshake ACK (Server trả lời). |
| **Byte 8 – 11** | `uint32` (Big-Endian) | **Field 8** | Mặc định `0x00000000` đối với gói gửi lên. |
| **Byte 12 – 15** | `uint32` (Big-Endian) | **Field 12 / Version** | `0x00000005` (số 5) đối với gói Handshake (Protocol v5).<br>`0x00000000` đối với các gói dữ liệu tiếp theo. |

#### Minh chứng toán học giải thích gói Handshake thực tế:
* Gói Handshake không có payload: `len(payload) = 0`, `total_len = 16` (`0x00 0x00 0x10`).
* `Byte 4..15`: `00 00 10 0a 00 00 00 00 00 00 00 05`
* Bước 1: $\text{CRC32}(\text{packet}[4:]) = \text{0xB93F3996} \rightarrow \text{Byte 2..3} = \mathbf{39 \ 96}$
* Bước 2: Ghép `Byte 2..15`: `39 96 00 00 10 0a 00 00 00 00 00 00 00 05`
* Bước 3: $\text{CRC32}(\text{packet}[2:16]) = \text{0xA25961DA} \rightarrow \text{Byte 0..1} = \mathbf{61 \ DA}$
* Kết quả ghép hoàn chỉnh:
  $$\mathbf{61 \ da \ 39 \ 96 \ 00 \ 00 \ 10 \ 0a \ 00 \ 00 \ 00 \ 00 \ 00 \ 00 \ 00 \ 05}$$
  *(Trùng khớp 100% từng bit với gói Handshake bắt được trong Wireshark!)*

### 3.6. Cơ Chế Giữ Kết Nối Định Kỳ (Heartbeat / Ping-Pong)
Máy chủ TCP Game sẽ tự động đóng kết nối (Socket Reset / Disconnect) nếu đường truyền không có dữ liệu qua lại trong 60 giây. Client cần duy trì cơ chế Heartbeat định kỳ:
* **Gói tin Client gửi:**
  ```json
  [{"func":"HeartBeat"}]
  ```
* **Body đóng gói URL Query String:**
  ```text
  bv=70.0.0&request=%5B%7B%22func%22%3A%22HeartBeat%22%7D%5D&seq=[seq]&session=[session_key]&sptype=spyuenan_md&version=73.0.0
  ```
* **Header:** 16 byte Header với `Flag 0x00`, `field_8 = 0`, `field_12 = 0`.
* **Server phản hồi:**
  ```json
  0;[{"func":"HeartBeatResult","serverTime":1790403150}]
  ```
* **Tần suất khuyến nghị:** Gửi lặp lại mỗi 25 – 30 giây trong một tiến trình nền (Background Thread / Timer).

### 3.7. Kỹ Thuật Đọc Luồng TCP & Bẫy Lệch Gói Cần Tránh (Critical Traps)

> [!WARNING]
> Đây là các nguyên nhân phổ biến nhất khiến bot/script bị kẹt kết nối hoặc crash mà tài liệu thông thường không đề cập:

1. **Bẫy lệch gói khi Bắt tay Handshake (Crucial Desync Trap):**
   * Ngay khi Client gửi gói 16-byte Handshake (`Flag 0x0A`), Server sẽ phản hồi **liên tiếp 2 gói tin TCP tách rời**:
     * **Gói 1:** JSON cấu hình máy chủ (`{"sid":2142,...}`).
     * **Gói 2:** Header 16-byte xác nhận Handshake ACK (`Flag 0x0B`, độ dài payload = 0).
   * **Sai lầm:** Nếu Client chỉ gọi hàm nhận 1 lần rồi gửi luôn gói `Login` (seq=1), thì khi đọc phản hồi của Login, Client sẽ đọc trúng Gói 2 (Handshake ACK) thay vì `LoginResult` $\rightarrow$ Toàn bộ luồng sau đó bị lệch pha và mất đồng bộ!
   * **Cách xử lý đúng:** Phải đọc đủ cả 2 gói tin TCP trước khi bắt đầu gửi gói `Login` (seq=1).

2. **Phân biệt `roleId` và `rid` khi gọi `bindZone` Web SDK:**
   * Sau khi tạo nhân vật thành công ở gói `seq=4`, gói `CreateAvatarResult` **KHÔNG** chứa ID hay UUID của nhân vật.
   * Client bắt buộc phải gửi tiếp gói `seq=5` (`QueryAvatarAttribute`) để Server trả về `avatarid` (UUID dạng chuỗi như `51ccf91b-e5c0-4e13-9c0d-da59abac9651`) và `rid` (ID số hiển thị như `142129994`).
   * Khi gọi `POST /bindZone`, tham số `roleId` **bắt buộc phải là chuỗi UUID `avatarid`**, tuyệt đối không truyền số `rid` hiển thị (nếu truyền số `rid` hệ thống Web SDK sẽ không ánh xạ đúng).

3. **Xử lý phân mảnh luồng TCP (TCP Stream Reassembly):**
   * Do đặc tính phân mảnh của giao thức TCP, một gói dữ liệu lớn (như phản hồi danh sách pet zlib) có thể đến trong nhiều chunk mạng.
   * Client bắt buộc phải đọc đúng 16 byte đầu tiên, trích xuất độ dài `total_len = int.from_bytes(header[4:7], 'big')`, sau đó chạy vòng lặp nhận cho đến khi đủ `payload_len = total_len - 16` bytes thì mới bắt đầu giải nén Zlib và parse JSON.

### 6.1. Script Python Đóng Gói Header Nhị Phân Lồng CRC32 (Socket Framing)
```python
import zlib

def pack_game_packet(flag: int, field_8: int = 0, field_12: int = 0, payload: bytes = b"") -> bytes:
    """
    Đóng gói 16-byte Header nhị phân lồng CRC32 theo chuẩn SJ::Net::Message::encode.
    """
    total_len = 16 + len(payload)
    b4_7 = total_len.to_bytes(3, "big") + bytes([flag])
    b8_15 = field_8.to_bytes(4, "big") + field_12.to_bytes(4, "big")

    # Tầng 1: CRC32 từ byte 4 đến hết payload
    data_after_4 = b4_7 + b8_15 + payload
    crc1 = zlib.crc32(data_after_4) & 0xFFFF
    b2_3 = crc1.to_bytes(2, "big")

    # Tầng 2: CRC32 trên 14 byte Header (byte 2 đến 15)
    data_2_15 = b2_3 + b4_7 + b8_15
    crc2 = zlib.crc32(data_2_15) & 0xFFFF
    b0_1 = crc2.to_bytes(2, "big")

    return b0_1 + b2_3 + b4_7 + b8_15 + payload

# Kiểm chứng Handshake
hs = pack_game_packet(flag=0x0A, field_8=0, field_12=5, payload=b"")
print(f"Handshake Hex: {hs.hex()}")
# Output: 61da39960000100a0000000000000005 (Khớp 100% gói bắt được!)
```

### 6.4. Script Python Đọc & Xử Lý Gói Tin TCP Stream (Unpack & Zlib Deflate)
```python
import socket
import zlib
import json

def recv_one_packet(sock: socket.socket, timeout: float = 5.0):
    """
    Đọc chính xác 1 khung gói tin nhị phân từ TCP Socket:
    1. Đọc đủ 16 byte header.
    2. Trích xuất total_len tại bytes 4..6.
    3. Đọc vòng lặp stream cho đến khi đủ payload_len.
    """
    sock.settimeout(timeout)
    header = b""
    while len(header) < 16:
        chunk = sock.recv(16 - len(header))
        if not chunk:
            return None, None
        header += chunk

    total_len = int.from_bytes(header[4:7], "big")
    payload_len = total_len - 16
    payload = b""
    while len(payload) < payload_len:
        chunk = sock.recv(payload_len - len(payload))
        if not chunk:
            break
        payload += chunk

    return header, payload

def parse_payload(payload: bytes):
    """
    Giải nén Zlib (nếu có) và bóc tách dữ liệu JSON.
    """
    if not payload:
        return None
    # Nhận diện Zlib Deflate magic bytes 0x78 0x9C hoặc 0x78 0xDA
    if payload.startswith(b"\x78\x9c") or payload.startswith(b"\x78\xda"):
        try:
            payload = zlib.decompress(payload)
        except Exception:
            pass

    text = payload.decode("utf-8", errors="ignore")
    # Bỏ mã trạng thái "0;" ở đầu phản hồi
    if text.startswith("0;"):
        text = text[2:]

    try:
        return json.loads(text)
    except Exception:
        return text
```

### 6.5. Script JavaScript / Node.js Đóng Gói Header 16-Byte Lồng CRC32
```javascript
/**
 * Tính CRC32 chuẩn IEEE 802.3 bằng thuần Javascript (Không cần thư viện ngoài)
 */
function crc32(buf) {
    let crc = 0xFFFFFFFF;
    for (let i = 0; i < buf.length; i++) {
        crc ^= buf[i];
        for (let j = 0; j < 8; j++) {
            crc = (crc >>> 1) ^ (-(crc & 1) & 0xEDB88320);
        }
    }
    return (crc ^ 0xFFFFFFFF) >>> 0;
}

/**
 * Đóng gói Header nhị phân 16-byte lồng 2 tầng CRC32 theo SJ::Net::Message::encode
 */
function packGamePacket(flag, field8 = 0, field12 = 0, payload = Buffer.alloc(0)) {
    const totalLen = 16 + payload.length;

    // Bytes 4..7: total_len (3 bytes big-endian) + flag (1 byte)
    const b4_7 = Buffer.alloc(4);
    b4_7.writeUIntBE(totalLen, 0, 3);
    b4_7.writeUInt8(flag, 3);

    // Bytes 8..15: field_8 (4 bytes) + field_12 (4 bytes)
    const b8_15 = Buffer.alloc(8);
    b8_15.writeUInt32BE(field8, 0);
    b8_15.writeUInt32BE(field12, 4);

    // Tầng 1: CRC32 từ byte 4 đến hết payload
    const dataAfter4 = Buffer.concat([b4_7, b8_15, payload]);
    const crc1 = crc32(dataAfter4) & 0xFFFF;
    const b2_3 = Buffer.alloc(2);
    b2_3.writeUInt16BE(crc1, 0);

    // Tầng 2: CRC32 trên 14 byte Header (byte 2..15)
    const data2_15 = Buffer.concat([b2_3, b4_7, b8_15]);
    const crc2 = crc32(data2_15) & 0xFFFF;
    const b0_1 = Buffer.alloc(2);
    b0_1.writeUInt16BE(crc2, 0);

    return Buffer.concat([b0_1, b2_3, b4_7, b8_15, payload]);
}

// Kiểm chứng Handshake
const hsPacket = packGamePacket(0x0A, 0, 5);
console.log("Handshake Hex:", hsPacket.toString("hex"));
// Output: 61da39960000100a0000000000000005 (Khớp 100% với Wireshark!)
```
